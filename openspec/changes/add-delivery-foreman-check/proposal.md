## Why
当前 ControlCCX 更像“驾驶室”：任务跑完后，用户往往不知道：
- 目标是否真的完成（尤其是复杂任务）
- 是否需要补做测试/自评/交付清单（工业级交付）
- 失败/阻塞时下一步该如何继续（resume prompt）

这会导致两类体验问题：
- **卡住感**：任务结束/失败后不知道下一步，容易刷新/重启服务。
- **交付质量不稳定**：复杂任务缺少自动化的“完成确认 + 交付检查”流程。

## What Changes
- 增加“交付前哨（Delivery Foreman）”自动流程：当某个 run 进入终态后，秘书（Observer）自动判断是否为复杂任务；若复杂则自动开启工业级交付检查。
- 工业级交付检查以“对话式引导”为主：自动生成下一步 resume prompt / 测试清单 / 自我评价与卓越标准引导；不默认自动执行危险操作。
- 提供可配置的开关（默认开启）：避免打扰或在低频场景关闭。

## Impact
- 前端：增加一次自动触发的“秘书对话”流程（可能自动发送一条 user 消息到 `/api/chat`），并记录已处理的 run，避免重复触发。
- 后端：无强制改动（复用现有 chat/observer），但可能需要补充更明确的提示与上下文组织方式。
- 风险：自动消息可能被认为“自动操作”。需要明确：
  - 默认仅生成建议/清单，不自动创建新 run、不自动运行测试。
  - 若未来支持“一键跑测试/一键继续”，必须再加显式用户确认。

## Open Questions
1) 触发范围：只对 `succeeded` 触发，还是对 `failed/blocked` 也触发“继续引导”？
2) 打扰程度：完成后是否自动打开 Secretary 抽屉，还是只显示 badge/提示并允许一键打开？
3) 复杂任务判断：用启发式（prompt 长度/多 run/产出长度/错误）还是直接让 Observer 判断？是否允许“成本上限”（避免每个小任务都调用 LLM）？
4) “工业级交付”定义：默认 checklist 里至少包含哪些（测试、build、lint、回归、文档、风险自评）？不同语言栈如何识别（Go/Vue）？
